# Заготовка для хакатонов по ИИ

Рабочий каркас ИИ-сервиса, который поднимается одной командой и уже умеет то,
что приходится делать на каждом хакатоне: принять датасет заказчика, показать
его, отвечать на вопросы по данным и документам, готовить документы, вести
журнал действий и считать метрику «было / стало». Предметная логика не
встроена — её вы пишете под конкретную задачу.

Собрана на основе прототипа ИИ-помощника АСЭЗ: предметная часть убрана,
каркас, дизайн-система и подключение к моделям оставлены.

---

## Быстрый старт

```bash
cp .env.example .env               # поменяйте APP_SECRET_KEY
docker compose up -d --build
docker compose exec ollama ollama pull qwen2.5:7b-instruct
```

Интерфейс — `http://<адрес>/`, вход: `ana` / `demo2026` (роли `ruk`, `exp`, `ana`).

Без Docker:

```bash
python -m venv .venv && . .venv/bin/activate
pip install -r backend/requirements.txt
cd frontend && npm install && npm run build && cd ..
python backend/scripts/make_demo_data.py data/samples/demo.xlsx --rows 500
APP_SECRET_KEY=dev uvicorn app.main:app --app-dir backend --port 8000
```

Модель не нужна, чтобы начать: без неё ассистент отвечает подобранными фактами,
а весь остальной контур работает. Это сделано намеренно — демо не должно падать
из-за того, что на машине жюри нет интернета или памяти под модель.

## Что править под свою задачу

По порядку, от самого важного:

1. **`.env`** — название сервиса, подпись, норматив ручной работы для метрики.
2. **`backend/app/ingest/loader.py`**, словарь `ROLE_HINTS` — какие колонки
   датасета считать ключом, названием, категорией, статусом, суммой.
3. **`backend/app/llm/prompts.py`** — роли пользователей, правила ответа,
   виды документов, которые готовит сервис.
4. **`backend/app/models.py`** — таблица `Record` бесформенная намеренно. Когда
   структура данных ясна, заведите предметные таблицы вместо неё.
5. **`backend/app/llm/assistant.py`** — функции `project_stats`, `find_records`,
   `record_facts`: что считать сводкой, как искать, что показывать модели.
6. **`frontend/src/pages/Assistant.tsx`**, массив `SUGGESTS` — подсказки, которые
   жюри нажмёт на демонстрации.
7. **`frontend/src/App.tsx`**, массив `TABS` — состав экранов.

Предметную логику (правила, расчёты, алгоритмы) кладите отдельным пакетом
`backend/app/domain/` — так её видно и не путается с каркасом.

## Безопасность и единый вход

Требования по безопасности есть почти на каждом хакатоне, и «логин с паролем в
SQLite» там выглядит слабо. Поэтому в заготовке есть вход через **Keycloak**:

```bash
docker compose -f docker-compose.yml -f docker-compose.keycloak.yml up -d --build
```

Realm, клиент, три роли и три пользователя заводятся автоматически из
`deploy/keycloak/realm-hackathon.json` — в админке настраивать нечего.
Консоль: `http://localhost:8080`, `admin` / `admin`.

Что сделано по делу, а не для галочки:

* Authorization Code Flow **с PKCE**, секрет клиента не обязателен;
* `id_token` проверяется по JWKS провайдера — подпись, срок, `issuer`,
  `audience`; без этого токен подделывается подбором тела;
* `state` и PKCE-verifier лежат в подписанной cookie и сверяются на возврате;
* роли ведутся в Keycloak и маппятся через `APP_OIDC_ROLE_MAP`;
* выход гасит и сессию провайдера, иначе следующий вход пройдёт молча;
* локальный вход остаётся запасным путём (`APP_LOCAL_LOGIN_ENABLED`) — если на
  защите Keycloak не поднимется, демо не умрёт вместе с ним.

На сервере обязательно поменяйте `KEYCLOAK_PUBLIC_URL` и `APP_PUBLIC_URL` на
реальные адреса: `issuer` в токене обязан совпадать с тем, что видит браузер.

Чего здесь нет и что придётся делать самим, если задача этого требует:
HTTPS и TLS-терминация, LDAP/AD, двухфакторная аутентификация, шифрование
данных, разграничение доступа к отдельным записям.

## Проверка перед сдачей

```bash
cd backend && python -m pytest tests -q     # 14 дымовых тестов
cd frontend && npm run build                # сборка и проверка типов
```

Тесты держат живым главное: вход, разбор файла, идемпотентность повторной
загрузки, ответ ассистента без модели, журнал, метрику и маппинг ролей.

## Ограничения

* Записи в `Record` хранятся как JSON — это удобно на старте и плохо для
  больших объёмов и сложных связей. Заводите свои таблицы, когда станет ясна
  структура данных.
* Эмбеддинги по умолчанию — hash-фоллбэк: он ищет по совпадению слов, а не по
  смыслу. Для настоящего семантического поиска поставьте
  `backend/requirements-ml.txt` (тянет torch, ~1,5 ГБ).
* Встроенный Qdrant держит папку эксклюзивно — только один рабочий процесс
  (`--workers 1`). Нужно больше — поднимайте Qdrant-сервер из
  `docker-compose.full.yml`.
* Демо-пользователи создаются при первом запуске. Перед показом наружу смените
  `APP_DEMO_PASSWORD` и `APP_SECRET_KEY`.
