## 3. Что реально оценивают

Формулировка организаторов: выявить сотрудников, уверенно использующих ИИ-инструменты и **агентный подход**, и сформировать ядро внутреннего ИИ-сообщества.

Это не конкурс продуктов. Оценивают метод работы с ИИ. Из этого следует:

- Демо должно показывать **как** решение сделано, а не только что получилось.
- Нужно уметь сказать: что декомпозировал, что отдал агенту целиком, где агент ошибся, как поймал.
- Голый работающий прототип без рассказа о методе недоберёт.

**Сигнал от члена жюри (Сергей Полозов, публично в чате):** при агентской разработке узкие горлышки — это анализ и QA, иногда параллельно с разработкой. Если в демо видно, что это горлышко закрыто, это попадание в его рамку.

## 4. Ограничения

- Данные только синтетические. Генерируются скриптом. Ничего корпоративного ни в репозитории, ни в промптах.
- Участие онлайн: **основной прогон демо локальный**. VPS — только резерв. Если демо уедет в сеть и канал моргнёт, выступление потеряно.
- Пять часов минус вступление и минус 30 минут на презентацию = **около четырёх часов на решение**. Соло.
- Соло означает один лимит токенов. Планировать работу так, чтобы упор в лимит не убивал демо.

## 5. Архитектура: ядро и линия отреза

Приложение делится на **каркас** (от темы не зависит) и **предметный модуль** (пишется в день Х).
Правило: ни одно имя из предметной области не попадает в каркас.

### Обязательное ядро — делать всегда

| Модуль | Что | Зачем |
|---|---|---|
| Запуск | `docker compose up` или один `python main.py` на чистой машине | ЗГД по ИТ, и просто чтобы демо не развалилось |
| LLM-слой | интерфейс `LLMProvider`, реализации `local` (llama.cpp, CPU) и `openai_compat`; выбор через `.env` | показать, что решение переносится в контур |
| Промпты | все в `/prompts/*.txt`, не в коде | кадры: поведение правится без разработчика |
| Предметный модуль | см. раздел 6 | собственно решение |
| Метрики эффекта | `config/economics.yaml` + виджет с **видимой формулой** | экономика и финансы |
| README | как запустить + раздел «Дальше»: 2 недели, квартал, владелец, топ-3 риска | проектный офис |

### Опциональное — по остатку времени, в этом порядке

1. **Аудит-журнал** — `audit_log`: кто, когда, что запросил, сколько заняло. Дёшево, сильный эффект на ИБ.
2. **Защитный слой** — валидация входа, таймауты, whitelist расширений файлов, ошибки без трейсбека.
3. **Роли** — три роли, разное поведение UI. Можно на заглушке без реального SSO.
4. **Keycloak / настоящий SSO** — **режется первым.** Соло за четыре часа это неоправданная трата. Если время остаётся — поднимать импортом готового realm, без ручной настройки.

### Отдельно про UI

Дизайн-токены корпоративного стиля лежат в `design-tokens.css` (отдельный файл).
Цвета там приближённые — сверить с Книгой фирменного стиля или вытащить с портала ЦПС через DevTools.
Шрифт: Helios Condensed лицензионный, в приложение не тащить. Замена — PT Sans Narrow / PT Sans, класть локально.
Логотип Газпрома в интерфейсе не использовать — только на титульном слайде презентации.

## 6. Точка расширения

Весь предметный код живёт в `/app/domain/` и реализует один интерфейс:

```python
class DomainTask(Protocol):
    name: str
    description: str
    input_schema: dict
    def run(self, payload: dict, user: User) -> DomainResult: ...

@dataclass
class DomainResult:
    summary: str                # короткий человекочитаемый итог
    payload: dict               # данные для отрисовки
    render_hint: Literal["table", "text", "chart", "list"]
    saved_minutes: float        # для расчёта эффекта
    citations: list[str] = field(default_factory=list)
```

Каркас отрисовывает любой из четырёх `render_hint` без доработки.
`domain/demo.py` — заглушка, чтобы каркас поднимался и показывался до появления реального модуля.

## 10. Презентация

Заготовка на фирменном шаблоне — `Хакатон_презентация_заготовка.pptx`, 7 слайдов:

1. **Титул** — название решения, дата
2. **Задача и решение** — задача слева, что умеет (01–04) справа
3. **Как делали: агентный подход** — постановка → ИИ → генерация → проверка → сборка. *Ключевой слайд под цель хакатона, стоит третьим намеренно*
4. **Почему это можно внедрять** — три колонки: безопасность / вписанность в ландшафт / люди и перенос
5. **Эффект** — формула рядом с числом
6. **Что дальше** — демо → план → пилот → риски
7. **Спасибо**

Черновой текст на слайде 4 — гипотезы. Проверить каждую строку под реальное решение, иначе на вопрос жюри придётся отвечать «вообще-то нет».

### Крючки под жюри

| Кто | Где | Не дольше |
|---|---|---|
| ИБ | слайд 4, левая колонка: данные, доступ, журнал | 40 с |
| Экономика и финансы | слайд 5: формула рядом с числом | 20 с |
| ЗГД по ИТ | слайд 4, средняя колонка: стек, запуск одной командой | 20 с |

Основное время — слайды 2 и 3. Крючки суммарно не больше 2,5 минут.

## 11. Стартовый промпт для Claude Code

Скопировать, подставить кейс, отправить первым сообщением:

```
Прочитай приложенный бриф целиком, прежде чем что-то делать.

Кейс хакатона: <вставить формулировку из объявления>

Задачи на первый шаг:
1. Предложи, что именно мы строим под этот кейс — одним абзацем, без кода.
   Назови render_hint из брифа и что будет считаться сэкономленной минутой.
2. Разбей работу на слоты по плану из раздела 8 брифа и скажи,
   что из опционального списка раздела 5 реалистично успеть.
3. Назови три места, где решение вероятнее всего сломается,
   и что проверять в каждом.

Не пиши код, пока я не подтвержу план.
Дальше работаем слотами: один слот — один сквозной результат, который можно показать.
После каждого слота коротко фиксируй: что сделал ты, что пришлось поправить мне.
Эти заметки идут на слайд про агентный подход, не теряй их.
```
